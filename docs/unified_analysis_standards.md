## 2. 阶段一：数据治理与基础指标口径

### 2.1 数据源

- 唯一正式数据源为项目中的 9 张 Olist 原始表及由其可重复构建的 SQLite 数据库。
- 原始 CSV 和原始数据库表不可执行人工覆盖、删除或直接修正；数据处理通过 View、CTE 或派生表实现。
- 所有正式结果必须能够从 `src/data_processing/build_sqlite_database.py`、项目 SQL 和 Python 脚本重新生成。

### 2.2 默认业务时间

- 订单、用户、GMV、地域、商品及支付分析统一使用 `orders.order_purchase_timestamp` 归属时间。
- 评论指标按订单购买时间归属，不使用评论创建时间作为默认统计月份。
- 配送指标仍按订单购买时间归属，配送时间字段仅用于计算时长和是否延迟。
- 自然月格式统一为 `YYYY-MM`，自然日格式统一为 `YYYY-MM-DD`。

### 2.3 数据粒度、主键和连接规则

| 对象 | 统一粒度或标识 |
|---|---|
| 订单 | `orders.order_id`，一行一笔订单 |
| 真实用户 | `customers.customer_unique_id` |
| 订单与客户表连接键 | `customers.customer_id`，只用于连接，不作为最终用户去重字段 |
| 订单商品 | `order_items.order_id + order_item_id` |
| 支付记录 | `order_payments.order_id + payment_sequential` |
| 评论明细 | `order_reviews.review_id + order_id` |
| 城市 | `customer_state + customer_city`，禁止只按城市名聚合 |

- 支付、商品、评论和地理表均可能形成一对多连接，必须先聚合到目标粒度再连接。
- 禁止将支付明细、商品明细和评论明细同时直接连接到订单后汇总，否则会放大订单数、GMV 或样本权重。
- 输出汇总必须能够回算总体：分组订单数、用户数、GMV 及占比应与相同口径的总体一致；因缺失值造成的差额必须单独披露。
- 所有比率、均值和增长率的分母为 0 时返回 `NULL`，不得改写为 0 或无穷大。

### 2.4 有效订单与支付订单

- 有效订单：`orders.order_status = 'delivered'` 的去重 `order_id`。
- 支付订单：有效订单中，订单级正支付金额大于 0 的去重 `order_id`。
- 有效订单量不因是否存在正支付记录而改变；支付订单量是另一指标，两者不得混用。
- 取消率是例外：分母为全部订单状态，分子为 `order_status = 'canceled'`，拼写固定为 `canceled`。

### 2.5 GMV、客单价和人均消费

- 有效支付记录：`payment_value IS NOT NULL AND payment_value > 0`。
- 支付表先按 `order_id` 汇总 `SUM(payment_value)`，再与有效订单连接。
- GMV 为有效支付且已送达订单的订单级支付金额总和，币种为 BRL。
- 无正支付的 delivered 订单不产生 GMV，但仍计入有效订单量。
- GMV 不等于 `order_items.price`，也不等于商品价格加运费；不同金额口径必须使用不同字段名。
- 客单价 AOV：`GMV / 支付订单量`，分母不是全部 delivered 订单量。
- 人均消费：`GMV / 唯一用户数`。
- 如业务附件需要 `GMV / 全部有效订单量`，字段名必须写为 `gmv_per_valid_order`，不得标记为 AOV。

### 2.6 商品销售额与运费

- 商品销售额使用 delivered 订单的 `SUM(order_items.price)`，不包含 `freight_value`，不得称为 GMV。
- 商品明细按 `order_id + order_item_id` 保持一行一件订单商品。
- 品类为空统一标记为 `unknown`，保留在品类销售占比分母中。
- 运费分析使用 `freight_value`；零运费可能代表免邮，保留并标记，不自动判错。

### 2.7 评论口径

- 有效评分范围为 1—5；评分为空或超出范围不进入评分指标。
- 同一订单多条合法评论在明细层保留；订单级指标只选 1 条代表评论。
- 代表评论按 `review_answer_timestamp DESC`、`review_creation_date DESC`、`review_id DESC` 稳定选择。
- 平均评论分数按订单级代表评论计算。
- 好评定义固定为 4—5 分；好评率分母为有有效代表评分的 delivered 订单。
- 评论标题和正文属于可选文本，缺失不等于评分数据错误，不进行无依据填补。

### 2.8 配送口径

- 配送时长：`实际签收时间 - 购买时间`，单位为天。
- 配送指标仅使用 delivered 订单，且相关时间非空、可解析、实际签收不早于购买时间。
- 合法长配送记录保留并标记，不因超出 IQR 上界自动删除。
- 延迟配送：实际签收时间严格晚于预计送达时间。
- 延迟配送率分母为实际签收和预计送达时间均有效、且首尾时间逻辑有效的 delivered 订单。
- 准时送达率只有在与延迟配送率使用完全相同分母时，才可写为 `1 - 延迟配送率`。

### 2.9 异常值、缺失值和清洗动作

- 原始数据不执行 `UPDATE` 或 `DELETE`。
- 缺失、异常和极端值必须区分为真实极端、明确错误和待复核，不得把统计极端直接等同于错误。
- 处理动作固定为 `retain`、`exclude`、`deduplicate`、`flag`、`correct` 五类；报告必须写明动作、影响范围和指标影响。
- `correct` 只有在存在唯一、可验证的替代依据时才能使用；当前阶段一数据质量结果没有可直接修正的记录。
- 金额、运费和配送时长统一以 IQR 作为正式异常识别方法：下界 `Q1 - 1.5 × IQR`，上界 `Q3 + 1.5 × IQR`。
- 四分位数使用稳定排序后的 nearest-rank 规则，具体实现见 `reports/data_quality/data_quality_report.md` 和 `sql/01_data_quality/data_quality_check.sql`。
- 3σ 可以作为补充敏感性检查，但不得替代 IQR 成为正式删除规则。
- 合法高金额、高价格、高运费、长配送、同订单多商品、多支付和多评论记录全部保留；是否进入特定指标由该指标定义决定。
- 非正支付不进入 GMV、AOV 和收入型 LTV；负价格或负运费从对应金额分析排除；零运费和零分期保留并标记待复核。
- 关键 ID、业务时间不可解析或关联主表不存在的记录，从相关分析 View 排除，但原始记录保留。
- 配送首尾时间缺失、不可解析或产生负配送时长时，不进入配送指标。
- 中间物流时间缺失或时序异常但首尾配送时长仍合法时，保留并标记；需要完整流程顺序的分析再单独排除。
- 缺失值不自动填 0；0、空字符串和 `NULL` 必须区分。
- 所有排除数量和占比必须能从数据质量汇总中追溯。

## 3. 阶段二：核心业务分析口径

### 3.1 数据覆盖和完整月份

- 当前 delivered 订单购买时间覆盖 `2016-09-15 12:16:38` 至 `2018-08-29 15:00:37`。
- `2016-09` 和 `2018-08` 不是完整自然月，只能保留作边界展示，不得参与正式峰值、低谷、环比异常、阶段划分或完整月份对比。
- `2016-11` 没有 delivered 订单。缺失月份保留为缺口或 `NULL`，不得擅自补成 0。
- 阶段二跨年同期正式对比统一使用相同且完整的月份范围，例如 `2017-01—2017-07` 对比 `2018-01—2018-07`。
- 已有 `2017-01—08` 对比 `2018-01—08` 的结果因后者包含不完整的 2018-08，只能作为探索性结果，不能作为正式同比结论。

### 3.2 月度 KPI、增长和季节性

- 月度公共层固定字段为 `month`、`gmv`、`order_count`、`average_order_value`、`new_users`、`active_users`，并统一限定为订单级正支付金额大于 0 的 delivered 订单；这是支付型月度分析层，不改变平台“有效订单量=全部 delivered 去重订单”的独立核心指标定义。字段细节见 `docs/monthly_kpi_dictionary.md`。
- 环比增长率：`(本月值 - 上一自然月值) / 上一自然月值`；同比增长率：`(本月值 - 上年同月值) / 上年同月值`。
- 前值缺失、月份不连续或分母为 0 时返回 `NULL`。
- GMV 驱动拆解使用 `GMV = monthly_kpi.order_count × AOV`；其中公共层 `order_count` 已统一为正支付 delivered 订单量，不得替换为全部 delivered 有效订单量。
- 节假日、季节性分析必须使用订单级正支付数据和 `customer_unique_id`；比较不同长度窗口时使用日均 GMV、日均订单量和 AOV。
- 节日前、中、后窗口及节假日日期较多，具体定义写在对应分析 SQL/报告中；同一节日在所有成员文件中必须复用同一日期表，修改时同步更新本文档和相关日期表。
- 数据只能支持相关性或结构差异时，报告使用“相关”“伴随”“可能解释”，不得直接写“导致”“提升了”或“造成了”。

### 3.3 支付结构、订单金额分档和州级结构

- 混合支付订单的支付方式 GMV 按各支付方式实际金额拆分。
- 需要给订单分配唯一支付方式时，取订单内聚合金额最大的支付方式；并列时按 `payment_type` 升序稳定选择。
- 订单金额按订单级正支付金额分为 `[0,50)`、`[50,100)`、`[100,200)`、`[200,500)`、`[500,+∞)`。
- 更完整的支付、订单金额与州级结构计算以 `sql/02_business_overview/04_business_structure.sql` 为准，但正式跨年比较必须使用完整且等长的月份范围。

### 3.4 月度趋势异常

- 正式月度趋势异常使用连续完整月份的环比增长率，并按每个指标的环比序列使用 `Q1 - 1.5 × IQR` 与 `Q3 + 1.5 × IQR` 判断。
- 当前月与上一个自然月不连续、任一月为不完整边界月或上月分母为 0 时，不计算正式环比异常。
- 2σ、固定 `±500%` 或“订单量低于 1,000”只能作为探索性诊断标签，不得与正式 IQR 异常混用；使用时必须单独命名并披露规则。
- 异常波动只能说明数据变化异常，外部事件原因必须有额外证据；没有证据时写“无法由现有数据验证”。

## 4. 阶段三：用户行为与价值分析口径

### 4.1 固定观察截止日

- 阶段三涉及 RFM、Cohort、7/30/90 日留存、生命周期、复购、流失及高价值用户交叉比较时，统一观察截止日为 `2018-07-31`，且只纳入 `order_purchase_timestamp < 2018-08-01 00:00:00` 的有效订单。
- 不使用程序运行日期作为截止日。
- `customer_profile` 当前包含 2018-08 数据，因此涉及上述跨成员比较时必须从订单级 `customer_order_base` 按固定截止日重新汇总，不能直接使用未截断的用户级结果。
- 若某项探索性画像使用全部数据，必须在标题、数据范围和图表注释中明确写“全观察期探索结果”，且不得与截至 `2018-07-31` 的结果直接合并比较。

### 4.2 用户、活跃用户和新增用户

- 真实用户统一按 `customer_unique_id` 去重，`customer_id` 不得用于最终用户计数。
- 活跃用户：在声明的统计窗口内至少产生 1 笔有效订单的唯一用户。
- 月活跃用户：在该自然月至少产生 1 笔 delivered 订单的唯一用户。
- 活跃用户不代表注册用户；不同月份的月活用户不能直接相加作为跨月唯一用户数。
- 报告中不能只写“有购买记录”，必须写明“至少 1 笔 delivered 订单”。
- 用户首购时间为完整可用历史或声明截止日前的第一笔有效订单时间。
- 新增用户为首购时间落在统计周期内的唯一用户，同一用户只能归入一个首购周期。
- 新增用户不是注册用户；数据观察期开始前历史缺失可能造成左截尾，报告必须披露。

### 4.3 复购用户、复购率和购买频次

- 复购用户：在同一声明统计窗口内拥有至少 2 笔去重有效订单的唯一用户。
- 复购率：`复购用户数 / 至少拥有 1 笔有效订单的用户数`。
- 平均购买频次：`有效订单量 / 活跃用户数`。
- 统计窗口内复购率、截至固定截止日的累计复购率和 Cohort 留存率是不同指标，禁止混用。
- 分组复购率必须先按用户汇总订单数，再将每个用户唯一分配到一个分组；不得在订单行上直接计算用户复购率。
- 平均复购间隔按用户购买时间排序，计算相邻两笔有效订单的间隔；首笔无间隔，负间隔排除并披露。项目正式总体口径对所有合法相邻订单间隔等权平均。

### 4.4 月度 Cohort 留存

- Cohort 月为用户首次有效购买的自然月。
- Cohort Month 0 为首购月，Month N 为首购月后的第 N 个自然月。
- 第 N 月留存率：`该 Cohort 在第 N 个自然月至少产生 1 笔有效订单的用户数 / Cohort 初始用户数`。
- 同一用户在同一自然月最多计 1 次。
- 只有完整经历第 N 月观察窗口的 Cohort 才能进入对应留存率比较；较新 Cohort 的右截尾单独标记为 `NULL`，不能填 0。

### 4.5 7/30/90 日短期留存

- 起点为用户第一笔有效订单的购买时间。
- N 日留存用户：首购后 `> 0` 且 `<= N × 24 小时` 内至少再次产生 1 笔有效订单的用户。
- N 日留存率：`N 日内再次购买用户数 / 具备完整 N 日观察窗口的首购用户数`。
- 完整观察窗口要求首购时间不晚于观察截止日减 N 日；窗口不足用户必须排除，并同时报告纳入人数和排除人数。
- 7/30/90 日留存不得与自然月 Cohort 留存混称。

### 4.6 生命周期长度与阶段

- 用户生命周期长度：截止日前最近一笔有效订单日期减首次有效订单日期，单位为天；单次购买用户为 0 天。
- 为避免成员自行设阈值，阶段三统一使用以下互斥顺序：
  1. 沉默用户：`recency_days > 90`；
  2. 首购用户：未沉默、有效订单数为 1，且 `recency_days <= 30`；
  3. 早期用户：未沉默、有效订单数为 1，且 `30 < recency_days <= 90`；
  4. 成长用户：未沉默、有效订单数不少于 2，且生命周期长度 `<= 180` 天；
  5. 成熟用户：未沉默、有效订单数不少于 2，且生命周期长度 `> 180` 天。
- 上述顺序先判断沉默，再判断订单数和生命周期，保证每位用户只进入一类。首次正式使用前必须在 SQL 中实现并完成互斥、完整性验证。

### 4.7 流失用户

- 流失用户：截至 `2018-07-31`，距离最近一笔有效订单严格大于 90 天的用户，即 `recency_days > 90`。
- 未流失用户：`recency_days <= 90`。
- 该定义是固定观察窗口下的行为型流失，不代表用户注销或永久离开平台。
- 分析流失关联因素只能表述为“相关特征”“数据差异”或“可能解释”，不得写成因果结论。

### 4.8 地域、星期和消费时段

- 用户地域使用客户州/城市，不使用卖家地域替代。
- 订单级分析使用该订单客户记录中的地址。
- 用户级画像使用截止日前最近一笔有效订单对应地址；同一购买时间并列时，按 `order_id DESC`、`customer_id DESC` 稳定选择。
- 城市必须以“城市 + 州”组合统计，禁止只按城市名称合并。
- 地理表只删除邮编、经纬度、城市和州五个字段完全相同的重复行；同一邮编的不同合法地理点全部保留。
- 星期序号固定为 Monday=1 至 Sunday=7。
- 工作日为 Monday—Friday；周末为 Saturday—Sunday。
- 小时按原始 `order_purchase_timestamp` 的 0—23 时统计，不进行未获数据支持的时区转换。
- 工作日/周末比较除总量外，应同时给出自然日数和日均订单量，避免因天数不同造成误读。

### 4.9 潜力区域市场

- 潜力市场的前期、近期窗口均使用连续 6 个完整自然月，且两段长度一致。
- 规模、增长和人均消费筛选阈值及 P25/P50/P75 规则以 `docs/customer_common_layer_dictionary.md` 为准。
- 分母为 0 的增长率保留为 `NULL`。
- “潜力市场”是历史数据筛选标签，不代表因果结论，也不自动等同于“下沉市场”。

### 4.10 RFM 与高价值用户

- RFM 数据只使用截至 `2018-07-31` 的 `customer_order_base`。
- Recency：观察截止日减最近有效购买日期，越小越好。
- Frequency：截止日前 delivered 去重订单数，越大越好。
- Monetary：截止日前订单级 GMV 之和，越大越好。
- R、M 使用经验分位点且同值同分；F 先对不同 Frequency 取值分档再映射回用户，不得把相同购买次数拆入不同分数。
- 高 R/F/M 固定为评分 `>= 4`，低 R/F/M 为评分 `<= 3`。
- 五类用户判断顺序和具体边界见 `docs/rfm_scoring_rules.md`，五类必须互斥且覆盖全部用户。
- 重要价值用户即高 R、高 F、高 M 用户；“高价值用户”如无其他说明，统一指这一类。
- 高价值用户渗透率：某地区重要价值用户数除以该地区全部用户数；分子分母使用相同截止日和相同代表地域规则。
- 高价值流失用户：同时属于重要价值用户且满足 `recency_days > 90`。由于 RFM 的高 R 与流失条件方向相反，如交集为空或很小必须如实报告，不得调整阈值迎合结果。
- RFM 是描述性分层，不包含成本、利润、营销触达或因果效果。

## 5. 阶段四：商品品类结构分析口径

### 5.1 公共层、订单范围与粒度

- 阶段四仅分析当前 Olist 原始数据及 SQLite 数据库中实际存在、可验证的字段；某项分析缺少必需字段时，直接跳过该项内容，不建立替代指标，也不补写对应 SQL、CSV、图表或报告结论。
- 阶段四正式分析仅使用 `order_status = 'delivered'` 的订单；公共层保留全部观察期数据，具体分析再按任务声明时间窗口。
- `category_item_base` 粒度固定为 `order_id + order_item_id`，一行一个订单商品，禁止因连接评论或支付明细产生重复。
- `category_order_base` 粒度固定为 `order_id + category_name`，同一订单包含多个品类时，每个“订单—品类”组合只保留一行。
- `category_sales_base` 粒度固定为 `category_name`，统一提供全观察期销售额、占比、品类订单量、商品件数、平均商品单价、每单件数和稳定销售排名。
- `category_monthly_sales_base` 粒度固定为 `purchase_month + category_name`，只保留实际发生销售的组合，不补 0 行，也不预先写入增长率或增长分类。
- 品类名称使用 `product_category_name_translation.product_category_name_english`；原始品类缺失、翻译表没有匹配记录或英文翻译为空时，统一标记为 `unknown`。
- `unknown` 必须保留在商品销售额、订单量、商品件数和占比分母中，不得为提高数据完整率而删除。
- 业务时间统一使用 `orders.order_purchase_timestamp`，月份统一为 `YYYY-MM`。
- 评论分析必须先按订单选出一条代表评论，再连接至订单—品类层；不得直接把评论明细连接到商品明细。
- 四个公共层的字段、构建 SQL 和质量校验见 `docs/category_analysis_dictionary.md` 与 `sql/06_product_analysis/category_order_base.sql`。

### 5.2 商品销售表现与数据可用性边界

- 品类商品销售额：delivered 订单内 `SUM(order_items.price)`，不包含运费，不得称为 GMV。
- 品类销售额占比：`品类商品销售额 / 全部品类商品销售额`；分母包含 `unknown`。
- 商品件数使用订单商品明细行数；同一订单中的合法多商品记录全部保留。
- 平均商品单价：`品类商品销售额 / 品类商品件数`。
- 每单件数：`品类商品件数 / 包含该品类的去重订单数`。
- Olist 原始数据没有商品成本、采购成本、佣金、营销成本、利润或实际履约成本。阶段四不计算商品利润、毛利、毛利率、高毛利品类、利润空间，也不建立任何经济性替代指标或基于成本/利润的经营建议。
- `freight_value` 可保留在订单商品公共层作为原始字段，但不纳入阶段四正式分析指标或结论。

### 5.3 时间窗口与品类增长

- `2016-09` 和 `2018-08` 为不完整自然月，只作边界展示，不参与正式增长比较、排名或增长分类。
- 正式品类增长窗口统一为 `2017-01—2018-07`。
- 月度商品销售额、订单量和商品件数均按购买月份统计；订单量按 `order_id` 去重。
- 环比要求当前月与上一个自然月连续；前值缺失、月份不连续或分母为 0 时返回 `NULL`。
- 月复合增长率使用 `CMGR = (期末销售额 / 期初销售额) ^ (1 / 间隔月数) - 1`。期初销售额为 0 或缺失时 CMGR 返回 `NULL`，并将相应品类作为新兴品类单独分析。
- 品类增长只能与平台整体增速比较，不能因缺少行业数据而写成“高于行业平均增速”。

### 5.4 品类满意度与评论文本

- 订单代表评论按 `review_answer_timestamp DESC`、`review_creation_date DESC`、`review_id DESC` 稳定选择。
- 平均评分、1 星差评率和 4—5 星好评率的分母均为该品类有有效代表评分的去重订单数。
- 1 星差评率：`1 星代表评论订单数 / 有有效代表评分的订单数`。
- 同一订单包含多个品类时，该订单的代表评论会进入其包含的每个品类；因此跨品类评论订单数可重叠，不得将各品类评论订单数直接相加回算平台去重订单数。
- 正式满意度排名只纳入有效评论订单数不少于 30 的品类，小样本品类保留但必须单独标记。
- 差评关键词只使用 1 星且正文非空的订单代表评论；关键词用于归纳投诉主题，不能直接认定投诉原因。

### 5.5 帕累托与关联规则

- 帕累托分析按品类商品销售额降序排列并计算累计占比；“头部品类”包含累计占比达到 80% 前的品类及首次跨过 80% 的品类，其余为长尾品类。
- 必须报告实际有多少个、多少比例的品类贡献至少 80% 商品销售额，不能预设一定符合“20% 品类贡献 80%”。
- Apriori 购物篮使用 `order_id`，商品项使用 `product_id`；仅纳入 delivered 订单，同一订单内相同商品先去重。
- 支持度分母为全部 delivered 订单，单商品订单必须保留在分母中。
- 商品级和品类级规则均至少输出共现订单数、支持度、置信度和提升度；正式筛选为共现订单数不少于 5、`confidence >= 0.10`、`lift > 1`。
- 达标规则不足 20 条时如实输出实际数量，可用品类级结果补充，但不得降低标准凑数。

### 5.6 品类 CMGR 计算与品类分类规则

- 计算品类 GMV 与平台整体 CMGR ：CMGR = (期末商品销售额 / 期初商品销售额)^(1 / 间隔月数) - 1
- 期初商品销售额：该品类或平台第一个有销售记录月份的 monthly_sales_amount。
- 期末商品销售额：该品类或平台最后一个有销售记录月份的 monthly_sales_amount。
- 品类定义：
  1. 明星品类：销售额 > 品类销售额中位数，且品类CMGR高于所有品类平均CMGR超过 5 percentage points；
  2. 潜力品类：销售额 ≤ 品类销售额中位数，但品类CMGR高于所有品类平均CMGR超过 5 percentage points；
  3. 稳定品类：CMGR ≥ 0，且未达到明星或潜力品类增长标准；
  4. 衰退品类：CMGR < 0；
  5. 新兴品类：观察期内首次出现销售，且无法计算有效 CMGR 的品类。

## 6. 报告与产出一致性

- 后续新产出的报告和文档，首行必须添加修改记录表，用于记录修改人和版本号：

```markdown
| 日期 | 修改人 | 版本号 | 备注 |
|---|---|---|---|
| YYYY-MM-DD | FL/FSH/HSZ | v1.0 | 本次修改内容 |
```

- 每次修改时新增一行记录，并填写修改日期、成员缩写、版本号和修改内容；不得覆盖已有记录。
- 报告正文必须明确：数据范围、观察截止日、有效订单、用户标识、金额口径、异常处理及引用的公共层。
- SQL、CSV、图表和报告必须来自同一次运行；报告中引用的文件路径必须是仓库相对路径，不得包含个人电脑绝对路径。

## 7. 发布前统一检查

三位成员提交阶段一至阶段四产物前共同确认：

1. 用户是否统一按 `customer_unique_id` 去重；
2. 有效订单是否统一为 delivered 去重订单；
3. GMV 是否先将正支付聚合到订单级；
4. AOV 分母是否为支付订单量；
5. 时间是否统一使用购买时间，边界月是否排除正式比较；
6. 阶段三结果是否统一截断至 `2018-07-31`；
7. 复购、留存、生命周期和流失是否使用本文档定义；
8. 支付、商品、评论等一对多表是否在连接前聚合；
9. 异常值是否先标记和分类，未将真实极端值直接删除；
10. 评论、配送、地域及工作日/周末规则是否一致；
11. 分组结果是否与总体对账；
12. 报告引用的文件路径是否为仓库相对路径。
13. 阶段四是否将商品销售额与 GMV 明确区分；
14. 品类缺失是否标记为 `unknown` 并保留在总体分母；
15. 评论是否先选订单代表评论，再连接商品或品类；
16. 是否出现利润、毛利率、高毛利品类、利润空间或经济性代理等无数据支持内容；
17. 正式品类增长是否排除不完整边界月，CMGR 分母为 0 时是否返回 `NULL`；
18. 帕累托是否报告实际达到 80% 所需的品类数量和比例；
19. Apriori 支持度是否以全部 delivered 订单为分母，规则不足 20 条时是否如实披露。
