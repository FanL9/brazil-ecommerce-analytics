## 二、本周重点问题与解决方法

### 1. GitHub 拉取共享进度时出现进程占用，无法正常同步

**问题：**  
在获取组内最新共享进度时出现进程被占用、无法正常 pull 的情况。作为刚开始使用 GitHub 进行多人协作的新手，最初对本地仓库、远程仓库、当前运行进程及 Git 状态之间的关系不够熟悉，只看单个报错难以快速定位问题。

**解决方法：**  
借助 AI 工具从项目整体流程出发进行排查，而不是只针对报错本身处理。逐步检查当前运行进程、Git 状态、本地代码与远程代码之间的关系，明确问题发生的位置后再处理冲突和占用状态，最终恢复正常拉取和同步。

**收获：**  
从“会执行 Git 命令”进一步提升到理解 GitHub 协作流程，开始能够主动判断本地与远程代码状态，而不是完全依赖固定命令。

### 2. 18 个 SQL 指标工作量较大，同时需要保证统计口径一致

**问题：**  
第二天需要完成 18 个 SQL 指标，后续又涉及订单、支付、客户、地域等多个分析模块。如果每个指标独立开发，很容易产生重复工作，也可能出现有效订单、GMV、订单数等核心指标在不同模块中口径不一致的问题。

**解决方法：**
1. 先明确有效订单、GMV、订单数等基础定义；
2. 建立订单级基础表，先处理支付等一对多数据带来的重复风险；
3. 各模块尽量复用统一基础数据；
4. 开发完成后进行跨模块总量校验，而不是仅检查 SQL 是否能够运行。

最终订单、支付、地域三个模块统一核对到 **96,477 个有效订单和 15,422,461.77 GMV**。

**收获：**  
认识到大量指标开发时，效率并不等于“更快地写 SQL”，而是尽早建立公共口径和可复用的数据基础，减少重复开发和后期返工。

### 3. 多来源指标接入看板后出现口径不一致

**问题：**  
不同模块在单独运行时结果正常，但接入同一个交互式看板后，由于数据粒度、筛选逻辑和统计口径不同，部分指标无法直接比较。

**解决方法：**  
重新核对每个模块的指标定义和数据粒度，优先统一订单、GMV、客户等基础口径，再处理展示层逻辑；不为了让图表“看起来一致”而直接修改结果。

**收获：**  
进一步认识到可视化的可靠性取决于底层指标口径。看板开发不仅是制作图表，更重要的是保证不同模块之间可以相互验证。

### 4. 低基数导致增长率失真，平台级指标与筛选器产生冲突

**问题：**  
部分分类或时间段基数很低，即使绝对变化很小，也会产生非常高的增长率；同时，一些平台整体指标作为基准值，本不应随局部筛选器变化，但在统一筛选逻辑下会被一起过滤。

**解决方法：**
- 对增长率同时检查基期规模，识别低基数造成的异常高增长，避免只根据百分比得出结论；
- 区分“动态分析指标”和“平台级基准指标”，根据指标用途决定是否响应筛选条件；
- 在看板中优先保证指标解释逻辑正确，再考虑交互效果。

**收获：**  
指标“计算正确”并不代表“业务解释正确”。需要同时判断分母规模、筛选范围和指标在分析中的角色。

### 5. 节假日前中后比较结构不清晰

**问题：**  
如果只按连续日期展示节假日附近的数据，很难直接判断节日前、节日期间和节日后的业务差异。

**解决方法：**  
按照业务问题重新划分比较窗口，将节假日前、节日期间、节日后作为明确的对比阶段，并在统一口径下比较核心指标。

**收获：**  
数据分析不仅需要选择指标，也需要设计合理的比较组。比较结构清晰后，指标才能更直接地回答业务问题。

### 6. 数据不足以支持增长策略的因果预测

**问题：**  
现有历史数据能够说明业务现状和相关关系，但不足以证明某项策略实施后一定能够带来确定幅度的增长。如果直接给出单一预测结果，会超出数据本身能够支持的结论范围。

**解决方法：**
1. 统一策略测算的基准口径；
2. 明确关键假设；
3. 分别设置 **保守、基准、乐观** 三种情景；
4. 用情景测算表达潜在收益范围，并保留假设条件。

**收获：**  
进一步理解相关分析、预测与因果判断之间的区别。数据不足时，应通过明确假设和情景分析表达不确定性，而不是把假设写成确定结论。

### 1. 流失用户分析

统一流失定义：

> 截至 2018-07-31，连续 90 天没有有效消费的用户。

计算逻辑：

```text
2018-07-31 - 最近一次有效购买日期 > 90 天
```

需要明确：该定义属于固定观察窗口下的行为型流失定义，不代表用户正式注销或永久离开平台。

主要工作包括：

- 识别流失用户并生成流失标记；
- 对比流失与未流失用户的用户数量及占比；
- 对比历史有效订单数、累计 GMV、人均消费、平均购买频次和复购率；
- 对比用户生命周期长度、最近一笔订单金额；
- 对比平均评论分数、平均配送时长和延迟配送率；
- 对比主要支付方式、州/城市分布和工作日/周末消费差异；
- 分析购买频次、累计消费金额、配送时长、延迟配送、评论分数、支付方式、地区、首次购买时间等特征与流失状态之间的关系。

结论中只使用“相关特征”“数据差异”或“可能解释”等表述，不直接将相关关系解释为因果关系。

### 4. 下周统一数据口径

阶段三继续遵循组内统一口径：

- 唯一用户：`customer_unique_id`
- 有效订单：`order_status = 'delivered'`
- GMV：有效订单的订单级支付金额
- 订单数：`COUNT(DISTINCT order_id)`
- 消费时间：`order_purchase_timestamp`
- 观察截止日：`2018-07-31`
- 复购用户：有效订单数不少于 2 笔
- 流失用户：截止日连续 90 天无有效消费
- 配送时长：实际送达时间减购买时间
- 延迟配送：实际送达时间晚于预计送达时间
- 评论分数：先聚合到订单级再参与分析

支付、商品、评论等一对多数据在关联前先聚合到订单级，避免订单数和 GMV 因重复连接被放大。
