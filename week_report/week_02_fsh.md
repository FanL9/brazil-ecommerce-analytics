## 二、本周重点问题、解决方法与能力提升

### 1. 公共数据层缺失与分析口径调整导致结果无法直接复用

**问题：**  
在流失用户分析开始时，部分预期公共数据层并不能直接满足当前分析需求，同时统一口径在项目推进过程中进一步明确。如果继续沿用已有中间结果，容易出现观察截止日、用户标识、有效订单范围或支付金额定义不一致的问题。

**解决方法：**
1. 不直接依赖不满足当前条件的中间结果，而是回到订单级基础数据重新确认字段来源和连接逻辑；
2. 按统一观察截止日重新汇总用户行为，明确唯一用户、有效订单、GMV、复购和流失定义；
3. 将关键步骤拆分验证，先核对用户数和订单数，再核对金额、评论和配送指标；
4. 对修改后的分析链重新运行，确保 SQL、CSV、图表和报告使用同一套结果。

**能力提升：**  
面对“结果对不上”这类问题时，我开始从单纯检查某条 SQL，转向追溯整个数据链路：先确认数据粒度，再确认指标口径，最后检查展示层。解决问题的方式更系统，也更容易定位真正的根因。

**本周收获：**  
公共数据层并不是“有表就能直接用”，而是必须确认其粒度、时间范围和指标定义是否与当前分析完全匹配。可复用的前提是口径一致，而不是文件名称相同。

### 2. 一对多数据连接造成订单数、GMV 和样本权重重复放大

**问题：**  
用户、支付、商品、评论等数据在订单维度上存在多种一对多关系。如果把支付明细、商品明细或多条评论直接与订单连接后汇总，会造成订单数、GMV 或评论样本重复放大。该问题在用户画像、品类满意度和关联规则等模块中都可能出现。

**解决方法：**
1. 明确每个分析模块的目标粒度，例如订单级、用户级、订单-品类级；
2. 支付数据先聚合到订单级，再与有效订单连接；
3. 评论数据先确定订单代表评论，再进入品类分析；
4. 用户指标先按 `customer_unique_id` 汇总，再计算复购率、流失状态和用户画像；
5. 每完成一个模块都进行总体回算，检查分组后的订单、用户和金额能否与统一总体对应。

**能力提升：**  
我对“一对多连接风险”的敏感度明显提高。现在在写 JOIN 之前，会先判断每张表的粒度和连接后可能产生的行数变化，而不是等结果异常后再排查。

**本周收获：**  
复杂分析中最重要的不是 JOIN 写得多快，而是始终知道“当前一行代表什么”。只要分析粒度不清楚，后续均值、占比、GMV 和用户数都可能失真。

### 3. 用户生命周期、流失和高价值画像的观察窗口需要保持一致

**问题：**  
流失、RFM、高价值用户和生命周期分析都涉及时间窗口。如果不同模块使用不同截止日，或者直接使用包含更晚数据的用户级结果，就会造成同一个用户在不同模块中的状态不一致。

**解决方法：**
1. 将用户分析统一截断到固定观察截止日 `2018-07-31`；
2. 从订单级用户行为数据重新计算最近购买、累计订单和累计 GMV；
3. 流失统一定义为截止日距离最近一次有效消费严格超过 90 天；
4. 高价值用户画像继续沿用同一截止日和用户标识，保证分子分母处于同一观察范围；
5. 对无法直接比较的全观察期结果单独保留，不与固定截止日结果混用。

**能力提升：**  
我开始更主动地检查“时间口径”，不再只关注 SQL 公式本身。对于留存、流失、生命周期这类指标，先确认观察窗口再计算指标，能够避免很多看似合理但实际不可比的结论。

**本周收获：**  
时间窗口本身就是指标定义的一部分。特别是用户分析中，右截尾和观察窗口不足并不是数据错误，而是需要在分析设计阶段主动控制的问题。

### 4. 关联规则 Support 分母与筛选标准需要严格统一

**问题：**  
商品关联规则分析中，如果 Support 只以多商品订单作为分母，会人为放大商品组合的出现概率；如果为了得到更多规则不断降低阈值，又会削弱结果的业务解释价值。

**解决方法：**
1. 统一以 `order_id` 作为购物篮；
2. 同一订单内相同商品先去重；
3. Support 分母使用全部 delivered 订单，单商品订单继续保留在分母中；
4. 统一使用共现订单数、Confidence 和 Lift 的正式筛选条件；
5. 达标规则不足目标数量时如实输出，不为了凑数量降低阈值；
6. 对商品级和品类级规则分别验证，确保公式、分母和输出逻辑一致。

**能力提升：**  
我在算法类分析中不再只关注“代码有没有跑出结果”，而是会进一步验证公式定义、分母范围和筛选条件是否与业务问题一致。

**本周收获：**  
算法输出并不天然等于可靠结论。越是 Apriori、RFM 这类带方法名称的分析，越需要回到业务定义检查每一个输入和分母，否则很容易得到形式正确但解释失真的结果。

### 5. 有效订单与支付订单概念混淆，影响业务结构结果的表达

**问题：**  
重新检查业务结构分析时发现，“有效订单”和“支付订单”在部分结果和字段名称中容易混用。虽然数据计算可以运行，但如果指标名称没有准确反映实际分母，就会导致不同模块之间难以对账，也会影响报告解释。

**解决方法：**
1. 重新梳理统一指标定义，明确 delivered 有效订单和正支付 delivered 支付订单是两个独立概念；
2. GMV、AOV、支付结构和订单金额结构按支付型口径重新规范；
3. 正式跨年比较采用完整且等长的 Jan-Jul 同期窗口，避免不完整边界月份造成伪差异；
4. 重新生成 SQL、Python、CSV 和图表，并逐一检查标题、字段名、时间范围和单位；
5. 最终三个业务结构模块统一回算到 **96,477 个支付订单和 15,422,461.77 BRL GMV**。

**能力提升：**  
我开始把“字段命名是否准确”也纳入分析质量检查，而不只验证数值本身。能够主动发现业务语义和计算口径之间的偏差，并重新整理整条分析链。

**本周收获：**  
数据结果正确只是第一层，指标名称、统计范围和业务含义同样必须正确。一个字段如果命名不准确，即使数字没错，也可能造成错误的业务理解。

### 6. Dashboard 跨模块整合时存在数据粒度、观察窗口和筛选逻辑冲突

**问题：**  
用户分析、商品分析和业务分析分别成立，并不意味着可以直接放入同一个 Dashboard。不同模块在数据粒度、观察窗口和金额口径上存在明显差异，例如 RFM 和流失分析使用固定截止日，商品销售额不能与 GMV 混用，部分平台级正式结果也不应直接响应全局筛选器。

**解决方法：**
1. 先为每个页面确认正式数据源和指标字典，再设计展示结构；
2. 将可以安全动态筛选的指标与固定观察窗口结果分开处理；
3. 对平台级或固定窗口结果保留原始口径，不为了增加交互效果强行套用全局筛选；
4. 在页面标题、单位和指标名称上明确区分 GMV、商品销售额、用户指标和商品指标；
5. 逐项核对 Dashboard 展示结果与正式 CSV，确保可视化没有改变底层分析含义。

**能力提升：**  
通过 Dashboard 整合，我开始从“做单个图表”转向“设计一个完整的数据产品”。不仅要考虑图表是否美观，还要处理页面结构、筛选逻辑、指标依赖和跨模块一致性。

**本周收获：**  
交互性不能高于分析口径。一个可靠的 Dashboard 不是所有图都能被筛选，而是每个筛选器都必须有明确的业务意义，并且不能破坏原有指标定义。

### 7. SQL、Python、CSV、图表和报告之间需要保持同一次运行的一致性

**问题：**  
分析不断修正后，如果只更新 SQL 或某一个 CSV，而没有同步更新脚本、图表和报告，很容易出现“代码是新版本、图表还是旧结果”的情况。多人协作时，本地修改和远端提交也可能发生版本交叉。

**解决方法：**
1. 重要口径调整后统一重新运行分析链，而不是只手工改某个输出文件；
2. 按 SQL -> CSV -> Python/图表 -> 报告 -> Dashboard 的顺序进行检查；
3. 提交前核对 Git 变更范围，确保不覆盖其他人的有效成果；
4. 出现多人并发修改时先整理本地提交，再通过 rebase 等方式同步并解决冲突；
5. 最终以正式 CSV 和统一口径作为结果核验依据。

**能力提升：**  
我对工程化交付和版本管理的理解进一步加深，能够从“完成自己的代码”转向“保证整套产物在团队仓库中能够稳定复现和继续使用”。

**本周收获：**  
完整的数据分析交付不是一个 SQL 文件，而是一条由代码、数据、图表、报告和展示组成的结果链。任何一环没有同步，都可能降低最终成果的可信度。

## 四、本周能力提升与学习总结

### 1. 复杂问题定位能力

本周遇到的问题已经不再是单一语法错误，而更多是数据层、口径、观察窗口和展示逻辑之间的组合问题。我逐渐形成了“先判断问题属于哪一层，再逐层缩小范围”的处理方式。

面对结果异常时，优先检查：
- 数据源和粒度是否正确；
- 时间窗口是否一致；
- 一对多连接是否造成放大；
- 分母和指标定义是否一致；
- 输出文件是否来自同一次运行。

这种排查方式提高了问题定位效率，也减少了反复修改局部代码带来的返工。

### 2. 数据口径治理能力

通过流失、RFM、业务结构、商品满意度和 Dashboard 的反复核对，我更加明确了指标口径在整个项目中的优先级。

我开始能够主动识别：
- 有效订单与支付订单的区别；
- GMV 与商品销售额的区别；
- 固定观察窗口与全观察期结果的区别；
- 用户级、订单级和订单-品类级粒度的区别。

这使我在后续分析中能够更早发现潜在风险，而不是等最终报告阶段再统一修改。

### 3. 结果验证与质量控制能力

本周大量工作并不是新增分析，而是重新验证已经完成的结果。通过总体回算、分组对账、跨文件核对和正式 CSV 验证，我进一步认识到质量控制本身就是数据分析的重要组成部分。

从业务结构三个模块最终统一到 96,477 个支付订单和 15,422,461.77 BRL GMV，到 Dashboard 页面逐项对应正式 CSV，我逐渐形成了“结果必须能够追溯和回算”的工作习惯。

### 4. 可视化产品整合能力

Dashboard 的进一步整合让我意识到，数据可视化不仅是图表设计问题，还包含数据产品逻辑。

需要考虑：
- 哪些指标可以动态筛选；
- 哪些指标必须固定观察窗口；
- 不同页面应该使用什么数据粒度；
- 用户、商品和业务结果如何在同一产品中保持口径一致；
- 如何让展示逻辑与业务分析逻辑保持一致。

这部分工作让我从单纯输出图表，逐步转向理解完整可视化产品的设计和验证过程。

### 5. 工程化协作与交付能力

本周同时维护 SQL、Python、CSV、图表、报告和 Dashboard，也经历了多人协作下的代码同步和提交冲突。

通过规范提交、检查变更、使用 rebase 处理并发修改以及重新验证最终产物，我对 Git 协作和可复现交付有了更实际的理解。相比单纯“把代码上传”，现在更关注是否能够安全合并、是否覆盖他人成果以及最终仓库能否稳定复现。

## 五、下周工作计划

下周工作将从“完成分析模块”进一步转向“问题总结、策略优先级和效果量化”，同时继续完成最终成果的一致性检查。

### 1. 策略优先级评估

基于前面业务结构、用户和商品分析中已经形成的问题与策略，建立统一的策略优先级评估框架，重点考虑：

- 预期效果；
- 实施难度；
- 投入成本或成本可控性；
- 策略适用对象和执行范围；
- 对 GMV、复购、留存或满意度等指标的影响方向。

通过统一评分标准形成策略优先级矩阵，并将策略划分为高、中、低优先级，避免只根据主观判断确定执行顺序。

### 2. 策略效果情景测算

对重点策略进行保守、基准、乐观三种情景测算。

计划重点评估：
- AOV 提升对 GMV 的潜在影响；
- 复购率改善可能带来的订单和 GMV 增量；
- 高潜力品类优化后的销售增长空间；
- 用户流失改善后的潜在价值保留；
- 重点策略的 ROI 或投入产出关系。

所有提升率继续明确为情景假设，不将历史相关性直接解释为未来因果效果。

### 3. Dashboard 最终完善

继续检查 Dashboard 中各模块的：
- 数据来源；
- 指标名称；
- 单位；
- 时间范围；
- 固定观察窗口；
- 筛选器适用范围；
- 页面展示结果与正式 CSV 的一致性。

在保证口径准确的前提下进一步优化页面逻辑，使 Dashboard 能够更清晰地体现从核心指标到业务结构、用户和商品分析的下钻路径。

### 4. 项目最终一致性检查

在项目进入最终整合阶段后，重点检查：

1. SQL、Python、CSV、图表和报告是否来自同一版本；
2. 用户是否统一按 `customer_unique_id` 去重；
3. 支付、商品和评论的一对多连接是否经过正确聚合；
4. GMV、商品销售额、有效订单和支付订单是否严格区分；
5. 用户分析是否使用统一观察截止日；
